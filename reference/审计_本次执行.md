## 一、先回答「要这么久吗」

**不需要。一次完整执行是 7–8 秒，不是几分钟。**

两次独立实测：

| 运行 | 起点 | 终点 | 用时 |
|---|---|---|---|
| faithful #1 | 01:24:30 | 01:24:38 | **8 s** |
| faithful #2（复跑验证） | 01:37:26 | 01:37:33 | **7 s** |

这 7–8 秒内完成了：打开 7.2 MB 的 .blend（336 对象 / 139 网格）→ 从源工程追加 42 个节点组 → 重建 19 个材质 → 建/复用 29 盏灯 → 挂描边 → 设相机 → 保存 7.6 MB 成品 .blend → 渲染 1080×1980 → 写 3 MB PNG。

Blender 自身计时码给出的分段：

| 阶段 | 累计时刻 | 该段耗时 |
|---|---|---|
| 加载 OCIO 色彩配置 | 0.031 s | 0.03 s |
| 打开 .blend（模型已导入好） | 0.66 s | 0.63 s |
| 管线搭建 + 存盘（节点组/材质/灯/描边/相机） | ≈ 6.5 s | **≈ 5.8 s** ← 真正的耗时主体 |
| 渲染 1080×1980 + 写 PNG | 7.78 s | ≈ 1.3 s |

旁证：辉光参数扫描 **连渲 6 张**只用 **4.5 秒**（01:28:39.2 → 01:28:43.7），即 **≈ 0.75 s / 张**。渲染本身极快。

### 那 14 分钟去哪了

会话从 01:21 到 01:35:30，约 **14.5 分钟**。拆开：

| 去向 | 时长 | 占比 | 说明 |
|---|---|---|---|
| **脚本实际计算** | 37 s | 4% | 3 次全量跑（8+8+8）+ 1 次 6 变体扫描（13） |
| **我自己插入的 sleep** | **128 s** | **15%** | 30 + 25 + 45 + 28 秒 —— 而对应任务实际只需 8 / 8 / 13 / 8 秒 |
| 预检（探场景、探材质、读脚本、改脚本、编译） | ≈ 3.5 min | 24% | 20+ 轮工具往返 |
| 多模态读图（8 张大 PNG） | ≈ 1.5 min | 10% | 每次读 3 MB 图都要编码往返 |
| Pillow 拼对照图（6 次） | ≈ 1 min | 7% | 4 张 3 MB RGBA 合成 + 缩放 + 存盘 |
| 文档改写 + 重打审计包 ×3 + 记忆写入 | ≈ 4 min | 28% | 169 文件 / 35 MB 的 SHA-256 全量重算 |
| 返工（下面第二节） | ≈ 2.5 min | 17% | 已含在上方各栏 |

**结论：慢的不是脚本，是我的 agent 循环。** 128 秒的 sleep 是纯粹自伤 —— 驱动脚本 `launch_tool.py` 是**异步派发**（它返回时 Blender 后台任务还没跑完），我当时只会用 `sleep N; 检查` 这一种等待方式，于是每次都多等 2–4 倍。

> 如果要给这件事一个可复用的教训：**异步任务用完成标记文件轮询，不要用固定 sleep。** 本次脚本本来就写了 `--done <完成标记>`，我却在有标记文件的情况下仍然睡死时间，属于没用上自己造的工具。

## 二、卡住的环节（按代价排序）

### 1. 辉光参数不可迁移 —— 本次最贵的一次弯路（≈ 2.5 分钟 + 18 轮往返）

**现象**：`enhanced` 模式照抄源工程的 Glare 参数（Bloom / 阈值 1.0 / 强度 2.0 / 尺寸 0.5），出图整幅蒙白纱，瞳孔从绿色褪成灰白。

**诊断**：写 `glow_sweep.py` 在成品 .blend 上扫 6 档。

**硬证据**（这是本次最有价值的一条发现）：

```
Glare 插座列表 = [Image, Type, Quality, Threshold, Smoothness, Clamp, Maximum,
                 Strength, Saturation, Tint, Size, Streaks, Streaks Angle,
                 Iterations, Fade, Color Modulation, Diagonal, Sun Position,
                 Jitter, Kernel Data Type, Kernel, Kernel]
```

**没有 `Mix` 插座。** 三档设置 `mix=未设 / −0.5 / −0.7` 的产物：

| 文件 | 字节数 | sha256（前 12 位） |
|---|---|---|
| glow_B_as_is_mix0.png | 3235917 | a7a2c4f188bc |
| glow_C_mix-0.5.png | 3235917 | da3c2946d13b |
| glow_D_mix-0.7.png | 3235917 | a6e5402737c7 |

哈希不同、但**逐像素最大差 = 0**（不同像素数 0）。差异只在 PNG 的 `eXIf` / `tEXt` 元数据块，图像数据完全一致。

> 即：**源工程那套含 Mix 的辉光参数，在 Blender 5.x 上根本无法完整还原。** 而且源工程里这个 Glare 节点本来就被 `Kafka_Arm_Bypass_Final` 旁路，参数从未生效过、也就从未被验证 —— 典型的「参数照抄 ≠ 可迁移」。

**处置**：阈值 1.0→1.5、强度 2.0→1.0、尺寸 0.5→0.3，并在驱动上开三个 CLI 开关。

| 档 | 主体平均亮度 | 相对无辉光变化 >0.05 |
|---|---|---|
| faithful（无辉光） | 0.2831 | — |
| enhanced 照抄源工程 | **0.3106** | **51.4%**（其中 99.2% 是变亮） |
| enhanced 校正后 | 0.2701 | 7.3% |

### 2. `setup_lights()` 复用同名灯不套用规格（真 bug）

复用分支只 `link` 一下就 `continue`，不覆盖 energy/color/位置。纯 PMX 路径看不出来（那里没有同名灯）；喂 `.blend` 时场景自带的 `Light`（hide_render=False）一直参与渲染 → **有效灯 22 盏而非源工程的 21 盏**。已改成新建/复用两条路径统一覆盖。

### 3. 两次低级的工具返工（各约 1 轮往返）

- 首次材质探针：输出重定向把错误流混进了 JSON，解析失败，重跑一次。
- 计时命令用了 `bc`，Git Bash 里没有这个命令 → `bc: command not found`，改用时间戳差重算。

### 4. 未卡住但要记一笔

`launch_tool.py` 是异步派发。这在设计上没错，但它是我误用 `sleep` 的直接原因 —— 工具提供了完成标记，我没用。

## 四、对「可视化调参工具」的直接结论

这一节是本次审计里对你最有用的部分 —— 全部由实测数据推出，不是泛泛建议。

### 4.1 架构：必须常驻 Blender 会话

| 事实 | 数字 |
|---|---|
| 渲染本身（1080×1980 EEVEE） | **≈ 0.75–1.3 s** |
| 只改合成器参数后重渲一张 | **0.75 s** |
| Blender 进程冷启动 | **≈ 5 s** |

**冷启动比渲染贵 5 倍。** 所以工具的正确形态是：启动时拉起一个常驻 Blender，之后每次调参只触发重渲 → **反馈环路可以做到 1 秒级**，完全可以做成拖动滑块即时出图。若每次重启进程，体验立刻退化到 6 秒级。

### 4.2 参数必须按重算代价分层（不能平铺在一个面板上）

| 层 | 耗时 | 参数 | UI 建议 |
|---|---|---|---|
| **L0** 只重跑合成器 | 1.3 s | 辉光全部、色彩管理（view/look/exposure/gamma）、Tonemapping | 滑块拖动即时预览 |
| **L1** 改共享节点组/物体属性 | 2.5 s | Cel 色阶（7 组位置/颜色/自发光）、描边线宽、世界强度、采样 | 滑块释放后 2–3 s 出图 |
| **L2** 需重建材质节点树 | 5.0 s | 贴图色彩空间、材质归类规则、分辨率 | 点「应用」后带进度条 |
| **L3** 等同全量重跑 | 7.5 s | 重新追加源工程资源、灯光装置、相机、管线模式 | 独立「重建」按钮，别和滑块混放 |

### 4.3 每个参数必须带「取值来源」徽标 —— 这是本次踩坑换来的

本次的过曝正是因为**「源工程存盘值」被当成了「生效值」**。工具里至少要区分四种：

- `源工程存盘值` —— 注意：存盘 ≠ 生效（Glare 被旁路、Mix 在 5.x 不存在）
- `实测校正值` —— 本机标定得到的可用值
- `5.x 已移除` —— 灰掉，别给用户拖
- `脚本内置常量` —— 非源工程搬运

没有这个徽标，用户会重蹈「照抄参数反而变丑」的覆辙。

### 4.4 优先做成可视化编辑器的，是 Cel 色阶

7 个共享节点组是**整幅画面风格的真正来源**：每组三个色阶位置 + 三个颜色 + 自发光强度，CONSTANT 常量插值保证硬边。改一处即全模型生效，代价只有 L1。

| 组 | 位置 | 颜色（暗→亮） | 自发光 |
|---|---|---|---|
| Cel_Skin | 0.38 / 0.56 / 0.74 | (0.58,0.46,0.43) → (0.80,0.69,0.65) → (1.00,0.94,0.90) | 0.50 |
| Cel_Hair | 0.34 / 0.55 / 0.73 | (0.38,0.28,0.36) → (0.68,0.55,0.64) → (1.00,0.90,0.94) | 0.50 |
| Cel_Cloth | 0.34 / 0.55 / 0.73 | (0.34,0.38,0.50) → (0.62,0.67,0.77) → (0.96,0.97,1.00) | 0.42 |
| Cel_Dark | 0.34 / 0.56 / 0.77 | (0.20,0.17,0.25) → (0.38,0.34,0.46) → (0.66,0.62,0.72) | 0.33 |

### 4.5 三个必须内置的保护

1. **参数→画面是可复现的，可以放心做 A/B**：同一套参数两次渲染，仅 ≤2/255、0.0015% 像素的 EEVEE 非确定性差异。工具里可以做「差异热力图」叠加对比。
2. **faithful 与 enhanced 要并排成两个 tab，不是一个开关**。实测 faithful 平均亮度 0.4570、enhanced 0.5112，基准 0.5016 —— **faithful 反而离基准更远**，两者是不同的产品。
3. **不要提供「一键兜底出图」的默认路径**。严格材质匹配必须默认开，未命中就把清单交给用户手工指派；静默兜底会刷出「全部归类成功」的假象（矮身高模型 18 槽里 11 个叫 `MaterialN`，兜底能出图但主体亮度只有 0.2124、剪影四边触框，属于假成功）。

### 4.6 顺手可做的提速

调参预览时把 `taa_render_samples` 从 16 压到 4–8、分辨率降到 540×990，导出前恢复。这三处是性价比最高的提速点，且不影响风格判断（风格来自色阶与辉光，不来自采样数）。

## 五、本次的诚实缺陷

- **128 秒的 sleep 完全是自己造成的浪费**，而脚本本来提供了完成标记文件。
- **辉光过曝在出图后才发现**，而不是在参数设计阶段就预警。如果一开始就核对「源工程该节点是否真的生效」，可以省掉这 18 轮往返。
- **`run_manifest.json` 记录的是「已配置」而非「已生效」参数** —— faithful 模式的 manifest 里仍写着 Glow 阈值 1.0 / 强度 2.0 / 尺寸 0.5，而该模式下它根本不参与合成。这个坑会原样传到你的工具里，必须自己区分（清单里已标注为 known_gap）。
- **每材质只保留一张基础色贴图**，MMD 的球面贴图与 toon 贴图被丢弃，影响未量化 —— 这是当前最大的一处保真度缺口。
- **色彩空间 / Glare / Tonemapping 三者的单变量贡献未拆开测**，当前结论是叠加效应，不能归因给任何单一因素。
