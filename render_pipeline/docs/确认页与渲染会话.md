# 确认页与渲染会话（v3.1）

> 目标：让「独立打开确认页」也能完成完整流程，同时**不破坏**现有的一键入口；
> 并且无论用户怎么点、怎么刷新，**都不会产生两个 Blender 进程**。

---

## 一、为什么把渲染任务收归服务端

加「页面按钮」之前，触发点只有一个（`开始渲染.py`）。
按钮一加就变成两个触发点 —— 两条路径各起一个 Blender 是最容易犯的错。

所以改成：

```
                         ┌──────────────────────────────┐
   开始渲染.py ──写 job──►│  确认服务（唯一渲染持有者）   │
        │                │   try_start_render()  ← 一把锁 │
        │  只轮询状态    │        ▲            ▲         │
        └───────────────►│        │            │         │
                         │  自动续跑 watcher   页面按钮    │
                         └──────────────┬───────────────┘
                                        │ 文件锁（跨进程）
                                        ▼
                                   Blender × 1
```

三层保护，缺一个都不够：

1. **同一入口**：自动续跑与页面按钮调用**同一个** `try_start_render(retry, actor)`，
   "检查 + 开始"整段在 `RENDER["lock"]` 内完成 → 并发请求只有一个能真正开始。
2. **进程内状态机**：`rendering` 中再次请求直接返回 `already=true`；
   成功后即使带 `retry` 也返回 `already_succeeded`。
3. **跨进程文件锁**（`_tools/render_lock.py`）：`O_CREAT|O_EXCL` 原子创建
   `<指纹>.render.lock`；即使 `开始渲染.py` 被跑两次、或另外起了一个确认服务，
   第二个也只能失败退出，不会真的起第二个 Blender。锁文件记录 pid / 来源 / 时间便于取证，
   陈旧锁（超时且 pid 不存在）会被回收。

`开始渲染.py` 走确认路径时**完全不调用自己的 `render()`**，只写 job、起服务、轮询状态。

## 二、状态机

```
waiting ──(全部确认)──► ready ──(自动或点击)──► rendering ──► success
                                                           ├─ rejected
                                                           ├─ diagnostic
                                                           └─ failed
```

| 状态 | 页面表现 | 按钮 |
|---|---|---|
| `waiting` | 等待确认 | 禁用，显示「还需确认 N 项」 |
| `ready` + 自动模式 | 可渲染 | 禁用，显示「正在继续渲染…」 |
| `ready` + 手动模式 | 可渲染 | 可点「开始渲染」 |
| `rendering` | 渲染中（第 k 次尝试） | 禁用 |
| `success` | **成品完成 ✓** | 可点「打开输出目录」 |
| `rejected` / `diagnostic` / `failed` | 非成品 + 失败原因 | 可点「重试渲染」 |

- 点击后**立即锁定**（`busy` 标志 + `disabled`），防双击与重复请求；
  锁定期间页面轮询只是 `GET`，不会触发渲染。
- **刷新页面不会重复触发**：渲染只由 `POST /render` 启动，而服务端状态是持久的。
- 失败后**确认结果保留**，重试不需要重新标注（确认已落盘到侧车映射）。
- 只有 `SUCCESS` 显示「成品完成」，判定取自 `run_contract.is_shippable()`，
  页面不自己做字符串比较。

## 三、HTTP 接口

```
GET  /                                 确认页
GET  /api/session                      待确认项 + 统计 + 会话 id + 渲染状态
GET  /api/session/<sid>/status          渲染状态（轮询用，轻量）
POST /api/session/<sid>/render          {"retry": true|false}
POST /api/session/<sid>/open-output     打开输出目录（仅 SUCCESS）
POST /api/answer                        写一条确认（原样保留）
GET  /previews/<file>                   预览图
```

**安全边界**

- 只监听 `127.0.0.1`。
- `sid` 由服务进程启动时随机生成（`secrets.token_hex(8)`）并注入页面；不匹配一律 404。
- **`/render` 只读 `retry` 这一个布尔量**，不读任何路径字段 —— 有源码级守卫测试。
- 渲染目标来自服务端登记的 job，并逐项复核：
  ① 指纹已在本会话登记 → ② 文件内容 sha256 等于该指纹 → ③ 路径位于素材根目录内；
  输出目录若越界（不在本工程内）会被清空。
- `open-output` 只在 `SUCCESS` 后可用，路径取自服务端记录，不来自请求。

### 4.1 自动化（`tests/test_render_session.py`，17 项，全过）

| 验收项 | 测试 | 结果 |
|---|---|---|
| 1. 不产生两个渲染任务 | `test_concurrent_start_only_one_wins`（6 线程并发） | ✓ 只有 1 个 `started=True` |
| 1′ 跨进程也不会两个 | `TestRenderLock`（3 项） | ✓ 第二个 `LockBusy`、陈旧锁可回收 |
| 2. 刷新不重复触发 | `test_repeat_request_returns_same_task` | ✓ `attempt` 不变 |
| 3. 浏览器不能提交路径 | `TestJobValidation`（5 项）+ 源码守卫 | ✓ 越界/未登记/指纹不符一律丢弃 |
| 4. 重复点击返回同一任务 | 同上 | ✓ `already=true, reason=rendering_in_progress` |
| 5. 只有 SUCCESS 是成品 | `test_only_success_is_shippable` | ✓ |
| 6. DIAGNOSTIC/REJECTED/FAILED 不得显示成品 | 同上 + `test_full_flow_...` | ✓ `shippable=False`，文案≠「成品完成」 |
| 附加：自检模式绝不产出成品 | `test_self_test_can_never_succeed` | ✓ 恒为 FAILED |

HTTP 层另有一组（`TestHttpSurface`）真实起服务验证：
未确认 → 409；伪造 `sid` → 404；带恶意字段并发点两次 → 只有 1 个任务、
`attempt==1`、执行的仍是登记目标（`C:/evil.pmx` 未生效）；终态非 SUCCESS 时不得留成品 PNG。

### 4.2 实机黑盒（`_tools/_e2e_auto_render.py`，一键入口自动续跑路径）

会话 `66b730a1c175ed8d` / 小贞.pmx / 端口 8773，结果：

```
✓ 初始状态 = waiting（auto_render=True，待确认 1 项）
✓ 服务端登记的目标 = 确认清单里的模型（浏览器无法替换路径）
✓ 未确认时 POST /render → 409「还有 1 项未确认」
✓ 并发点击 4 次都没有启动渲染，attempt 仍为 0
✓ 确认写回成功
✓ 确认后服务端自动开始渲染 {"started": true, "already": false, "reason": "started"}
✓ 渲染中 3 次并发点击全部 started=False，
  reason = rendering_in_progress
✓ attempt 仍为 1 —— 没有产生第二个渲染任务
✓ 非 SUCCESS → shippable=False、页面不得显示成品完成、不留成品 PNG
```

**这一次渲染本身是 FAILED，原因是环境而非流程**：常驻 Blender 通道
（`127.0.0.1:9876`）当时不在线。Blender 可执行文件通过 `--blender` 或
`TOON_BLENDER` 提供，作为本机直接启动的回退；仓库不保存安装路径。
诊断已从原来的「`(worker)` 渲染线程异常」改成可读的两行说明 + 处理办法，
页面在通道未就绪时也会提前显示警告。

> 因此：**状态机的不变量（单任务、幂等、路径隔离、终态口径）已实测通过；
> 真实 Blender 产出 SUCCESS 的那一段，需要在 Blender 开启 9876 监听后再跑一次。**
> 重跑命令见第 5 节。

## 五、怎么用

```bash
# A. 一键入口（推荐）：需要确认时自动打开页面，全部确认后自动继续渲染
python 开始渲染.py --pmx "模型.pmx"
python 开始渲染.py --fingerprint 545a9ba0
python 开始渲染.py --fingerprint 545a9ba0 --maps-dir reports/_e2e/maps_auto2   # 试跑用隔离映射

# B. 独立打开确认页：确认完后自己点「开始渲染」
python _tools/confirm_server.py --all --port 8770 --open

# C. 只验流程状态机、不开 Blender（结果恒为 FAILED，绝不可能是成品）
python _tools/confirm_server.py --all --self-test --port 8770

# D. 黑盒验收（需先有一个在跑的会话）
python _tools/_e2e_auto_render.py --port 8773 \
       --confirm-file reports/confirmation/<指纹16位>_confirmation.json
```

渲染前确认常驻通道在线：`netstat -ano | grep :9876`（空 = 未就绪）。
