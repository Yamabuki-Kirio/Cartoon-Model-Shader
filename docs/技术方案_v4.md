## 1. 已定决策（不可自行更改）

| # | 决策 |
|---|---|
| 1 | 动态对象身份 = **「对象类型 + datablock 名称/来源」**（会话身份，作主键）。结构指纹**只负责检测变化**，不用于匹配。重命名 ⇒ 基线失效、要求刷新，**不做猜测迁移** |
| 2 | 指纹分**身份 / 结构 / 值**三层。只有结构变化（对象增删、节点拓扑、色标数量、材质槽）使草稿与确认令牌失效；普通值变化按**外部改动报告**，非致命 |
| 3 | ColorRamp 色标数量变化 = 结构变化 ⇒ 旧草稿与保存确认令牌作废 |
| 4 | 灯光变换用**世界空间**；带动画/驱动/约束/父级的灯光默认只读并告警，**不写 `location`** 冒险修改 |
| 5 | 管理范围来自**明确清单 / 专用集合 / 已有规格表**，不靠名称猜测；无法证明受管的一律只读 |
| 6 | `asset` 只提交服务端生成的资源 ID，浏览器**永不**提交文件路径 |
| 7 | 撤销/重做 = **独立草稿命令栈子系统**（纯客户端），不混入布局代码 |
| 8 | 性能沿用需求文档：L0 P50 ≤1.5s / P95 ≤3s；L1 P50 ≤3s / P95 ≤5s；L2 P95 ≤8s；L3 P95 ≤12s。**混合修改只执行一次**，按最高成本层级调度 |
| 9 | 双向覆盖断言**限定在「工具声明管理的 binding」**：探针 binding 与 schema binding 的双向差集必须为空。不声称覆盖 Blender 全部可写属性 |
| 10 | 删除文档中固定的「总项数」表述，统一改为「静态 schema 与运行时能力探测共同决定」 |

前端：Vite + Preact + TypeScript + Vitest + 轻量自研虚拟列表。
FastAPI 只托管构建产物。旧原生页面迁移期作行为参照，**最终不得并存两套正式 UI**。
令牌由运行时 HTML 响应注入，**不进入构建产物、不进入日志**。

### 1.1 L3 的处理（决策 1 补充，来自用户复核）

**`ROLLBACK_NOT_POSSIBLE` 不作为 L3 的正常能力。** 在可靠恢复机制完成前，L3 参数**只能探测和只读展示**。

实施顺序：

1. 先建立**结构性操作前检查点**；
2. 验证失败后能恢复**节点、灯光、相机、材质关系和工程路径**；
3. 恢复后进行**结构指纹与关键值回读**；
4. **只有验证通过的 L3 操作才标记为可编辑**。

无法安全恢复的项返回：

```json
{"supported": true, "editable": false, "readonly_reason": "rollback_unavailable"}
```

不允许「执行后再让用户人工收拾」。因此 v4 早期阶段 L3 节点全部 `editable: false`，
直到检查点机制通过验收测试。

### 1.2 只读拓扑导出的形状

**`GET /api/diagnostics/describe`**（只读，因此不校验令牌，与「全部写接口需令牌」的既有规则一致）。

输出必须脱敏，**不包含**：工程绝对路径、贴图绝对路径、令牌、任意用户目录。
**只保留**：datablock 名称、类型、结构、能力、必要指纹。

## 2. 现状核对：改造点在哪

| 现状 | 位置 | v4 要求 | 性质 |
|---|---|---|---|
| `binding` 是字符串键（`view.exposure`、`glare.Threshold`） | `src/server/params.py` | `binding = {object_type, object_id, field}` | 契约变更 |
| `_stage_of()` / `_write_line()` 按字符串前缀静态分发 | `src/server/blender_ops.py` | 数据驱动模板表 + 依赖图排序 | **重写写入骨架** |
| 回读手写 view/glare 两段 | `blender_ops.build_read_code` | 按声明 binding 通用回读 | **重写回读骨架** |
| 白名单校验 `k not in params.BY_ID` | `session.validate_draft` | 对**基线实时 id 集合**校验 | 契约变更 |
| 值只有一维 | `session.Baseline` | 三层 + `effective/active/supported/editable` | 契约变更 |
| L0 单档 300ms 去抖 + 单合并线程 | `session.PreviewService` | L0–L3 分层调度 + 合并 + 取消 | 扩展 |
| 撤销/重做无实现 | `src/` 0 命中（需求文档 128/202/359 有要求） | 独立命令栈 | 新子系统 |
| 前端 47KB 原生 JS、无框架 | `src/web/app.js` | Vite+Preact+TS | 重写 |

**结论**：提交 1 必须交付**一条端到端竖切**（Cel），而不是「schema + 空布局」。
若先铺 UI 外壳，schema 形状在执行器落地时很可能被推翻，外壳会跟着返工。

## 3. 三层身份模型

### 3.1 身份层（主键）

```python
@dataclass(frozen=True)
class ObjectIdentity:
    object_type: str   # "NODE_GROUP" | "LIGHT" | "MATERIAL" | "CAMERA" | ...
    name: str          # Blender datablock 名（重命名即失效）
    source: str        # 来源：集合名 / 父节点组 / 所属对象

    def key(self) -> str:
        return f"{self.object_type}:{self.source}/{self.name}"
```

**不使用指纹做匹配**：两个对象可能结构完全相同，指纹会误匹配（决策 1）。

### 3.2 结构层

`structure_hash` = 对**受管对象集合**求哈希，内容为 `{identity_key → 结构签名}`。
结构签名只含：节点名+类型+连接数、ColorRamp 色标数量、材质槽数量、受管对象集合本身。
**值不进哈希**。

### 3.3 值层与失效规则

| 变化 | 草稿 | 确认令牌 | 对外表现 |
|---|---|---|---|
| 身份层：受管对象被重命名/删除 | 作废 | 作废 | `409 IDENTITY_MISSING`，列出受影响参数，要求刷新基线 |
| 结构层：`structure_hash` 变化 | 作废 | 作废 | `409 STRUCTURE_CHANGED`，列出结构差异 |
| 值层：外部改了某个值 | 保留 | 保留 | 非致命，报 `external_changes: [{id, baseline, current}]` |

`GET /api/session/baseline` 新增字段：

```json
{
  "baseline_id": "a1b2c3d4e5f6",
  "schema_version": "toon-surface/2",
  "structure_hash": "9f2c41ab…",
  "identity": {"managed_objects": 14, "kinds": {"NODE_GROUP": 7, "LIGHT": 5, "MATERIAL": 2}},
  "managed_scope": {"source": "pipeline-manifest", "manifest_id": "…"},
  "external_changes": []
}
```

## 4. 递归 schema（`schema_version = "toon-surface/2"`）

### 4.1 节点公共字段

`id` / `kind` / `group` / `cost` / `label` / `active` / `supported` / `editable` /
`readonly_reason` / `value_source` / `binding`。

`kind` ∈ `float | int | bool | enum | color | vector | asset | resolution | ramp | table | rules | group`。

`cost` ∈ `L0 | L1 | L2 | L3`。

`value_source` ∈ `scene | default | draft | unsupported`。

标量附带 `value / baseline / effective` 与约束；结构字段附 `structural: true`；
动态对象附 `identity`；有影响的附 `impact`。

### 4.2 示例：标量（现有 L0 的等价迁移）

```json
{
  "id": "color.exposure", "kind": "float", "group": "color", "cost": "L0",
  "label": "曝光 (EV)", "unit": "EV",
  "binding": {"object_type": "VIEW_SETTINGS", "object_id": "$scene", "field": "exposure"},
  "minimum": -10.0, "maximum": 10.0, "step": 0.02,
  "value": 0.0, "baseline": 0.0, "effective": 0.0,
  "active": true, "supported": true, "editable": true, "readonly_reason": null,
  "value_source": "scene"
}
```

**为什么 `ramp` 是复合而非展开成 2N 个 id**：Blender 的 ColorRamp 是单个 datablock，

「每个色标的位置 / 每个色标的 RGBA」），写入路径永远走整体替换。

### 4.5 字段白名单 = 注入防线

`binding.field` **不来自请求**，只能来自 schema 声明；`(object_type, field)` 必须命中白名单，
否则在**应用启动时**（`create_app`）抛错 —— 而不是等某个请求落到 Blender：

| object_type | 允许的 field |
|---|---|
| `SCENE` | `frame_current`(只读) |
| `VIEW_SETTINGS` | `exposure`, `gamma`, `view_transform`, `look` |
| `DISPLAY_SETTINGS` | `display_device` |
| `RENDER` | `engine`, `resolution_x`, `resolution_y`, `resolution_percentage`, `film_transparent` |
| `IMAGE_SETTINGS` | `file_format`, `color_mode`, `color_depth` |
| `WORLD` | `color`, `use_nodes`, `node.strength` |
| `NODE_GROUP` | `mute`, `topology`(只读) |
| `COLOR_RAMP` | `elements`, `interpolation`, `element_count` |
| `LIGHT` | `energy`, `color`, `type`, `hide_render`, `use_shadow`, `matrix_world.translation`, `matrix_world.rotation` |
| `CAMERA` | `lens`, `sensor_fit`, `sensor_width`, `sensor_height`, `shift_x`, `shift_y`, `type`, `ortho_scale` |
| `CAMERA_DOF` | `use_dof`, `focus_distance`, `aperture_fstop` |

## 5. 执行器数据流

```
① 探测（只读）      build_probe_code(schema, scope)
        ↓               逐个受管对象读身份 + 结构签名；逐个 binding 读值
        ↓               print("__TOON_JSON__" + json.dumps(payload))
② 建 schema         probe → 递归 schema（值/基线/生效/能力/可编辑 + 动态对象身份）
        ↓
③ 客户端草稿        {id: value}（稀疏，含复合节点的整体值）
        ↓
④ 服务端校验        id ∈ 基线实时 id 集合；kind 校验；范围/枚举/依赖；supported/editable 检查
        ↓
⑤ 生成 plan         [{stage: L0|L1|L2|L3, ops: [{binding, setter_template, value}]}]，阶段内按依赖拓扑排序
        ↓
⑥ 应用（原子）      build_apply_code(plan)：快照 → 按序写入 → 失败整体回滚
        ↓
⑦ 回读校验          build_readback_code(plan)：只读回 plan 涉及的 binding，逐项比对
        ↓
⑧ 渲染 / 回滚       沿用现有「恢复基线 → 渲染 → 恢复基线并校验 + rollback 三态」
```

性质（沿用既有不变量）：

* 只读探针在 `finally` 中恢复它碰过的一切（`color_looks` 的 `finally` 恢复范式）；
* 单个 binding 读取失败**不中断**整体探测，降级为 `supported: false` + `reason`；
* 所有进入模板的字面量 `repr()` 量化；
* **阶段顺序固定** L0 → L1 → L2 → L3；阶段内按 `depends_on` 拓扑排序。
  现有硬规则「`view_transform` 必须先于 `look`」变成一条显式边，删掉字符串前缀猜测；
* 快照集合由 plan 的 binding **推导**，不再硬编码 view_transform/look/exposure/gamma；
* L3 结构性操作在检查点机制通过验收前一律 `editable: false`（见 §1.1）。

## 6. 错误码

新增（全部登记 `errors._ERROR_META`）：

| 码 | HTTP | retryable | 触发 |
|---|---|---|---|
| `STRUCTURE_CHANGED` | 409 | true | 结构层指纹不符：草稿与确认令牌作废，要求刷新基线 |
| `IDENTITY_MISSING` | 409 | true | 受管对象被重命名/删除 |
| `UNSUPPORTED_PARAM` | 400 | false | 写入 `supported: false` 的参数 |
| `NOT_EDITABLE` | 400 | false | 写入 `editable: false` 的参数（含 `rollback_unavailable`） |
| `ASSET_UNKNOWN` | 400 | false | `asset` id 不在当前基线资源表 |
| `PRESET_INCOMPATIBLE` | 409 | false | 兼容性报告存在阻断项，需用户显式确认 |
| `FRONTEND_NOT_BUILT` | 503 | false | 未构建 `dist/`，服务端明确诊断而非返回残缺页面 |

非致命：`external_changes`（值层外部改动）只报告，不升为错误码。

**不再需要** `ROLLBACK_NOT_POSSIBLE` 作为 L3 的常规错误 —— 不可安全恢复的 L3 参数
在探测阶段就标 `editable: false`，根本不进入执行路径。

## 8. Cel 竖切设计（提交 1）

### 8.1 探测策略：先描述、再声明

无法在本机检查真实 `.blend`，因此：

1. 先交付 `GET /api/diagnostics/describe`：把受管节点组拓扑原样 dump（节点名、类型、连接、
   ColorRamp 元素数、找到/未找到的插座），**脱敏后**返回；
2. schema 生成器**以探测结果为准**：找到就生成可编辑节点；找不到就生成
   `supported: false, editable: false, reason: "未在节点组中找到对应插座"` 的**只读**节点；
3. **绝不猜 socket 名**。真机输出回传后才冻结 Cel schema。

### 8.2 id 规则

```
cel.<group>.enabled                bool    L1
cel.<group>.ramp                   ramp    L1
cel.<group>.ramp.element_count     int     L3   structural, editable:false
cel.<group>.ramp.interpolation     enum    L1
cel.<group>.emission_strength      float   L1   （探测到才生成）
cel.<group>.impact.material_count  int     —    只读
cel.<group>.managed_mode           enum    —    只读（编辑 / 只读探测 / 回退）
```

`<group>` ∈ `Cel_Skin / Cel_Hair / Cel_Cloth / Cel_Dark / Cel_Eyes /
RayToon_Face_Soft / RayToon_Eyes_Unlit`；`Sakura_Hair_Reference` 以只读节点呈现在同组下。

### 8.3 竖切验收链

```
运行时探测 → 递归 schema → Cel 控件 → 草稿校验 → 固定模板写入 → 回读 → 预览 → 完整回滚 → 预设与保存令牌绑定
```

| 环节 | 断言要点 |
|---|---|
| 探测 | fixtures 提供 ColorRamp + 7 组；探测输出含全部元素；`supported:false` 路径可达 |
| 脱敏 | 输出不含绝对路径/令牌/用户目录（比照现有 `redact` 断言手法） |
| schema | id 唯一；每个节点有 kind/cost/binding；`element_count` 标 `structural: true` 且 `editable: false` |
| 控件 | 复合 `ramp` 渲染出 N 组 position/color 控件 |
| 草稿校验 | 位置越界拒绝；颜色非 4 元拒绝；未知 id 拒绝；`supported:false` ⇒ `UNSUPPORTED_PARAM`；`editable:false` ⇒ `NOT_EDITABLE` |
| 写入 | 整体替换 ramp；写入后**元素数不变**；字面量经 `repr` |
| 回读 | 逐元素比对；注入偏差 ⇒ `APPLY_VERIFY_FAILED` + 回滚 |
| 预览 | job 走完整链路，`cost == "L1"` |
| 回滚 | 中途失败后所有 Cel 组逐项回到基线 |
| 结构变化 | 元素数变化 ⇒ `STRUCTURE_CHANGED`，草稿作废，旧令牌 ⇒ `BASELINE_STALE` |
| 重命名 | 组改名 ⇒ `IDENTITY_MISSING`，受管参数转 `supported:false`，草稿作废 |
| 令牌绑定 | 预设存 Cel 图；篡改任一色标 ⇒ `COMMIT_TOKEN_MISMATCH` |
| 双向覆盖 | §9 |

### 8.4 提交 3A 落地记录（已实现，代码为准）

上面 §8.1–8.3 是**设计意图**；本节记录实际落地时与设计不同的地方，以及原因。
凡与本节冲突的，以本节为准。

**① 过渡接口。** 迁移期新增四个 v4 接口，旧 L0 接口与旧页面**一行不改**：

```
GET  /api/v4/surface/schema      递归 schema（Cel 竖切；只读，不校验令牌）
GET  /api/v4/session/baseline    v4 基线（身份 + 结构指纹 + 基线值 + 降级清单；只读）
POST /api/v4/preview             L0 + Cel 编进同一任务（写接口，校验会话令牌）
GET  /api/v4/jobs/{job_id}       与 /api/jobs/{job_id} 共用同一份任务存储
```

基线仍然由 `POST /api/session/baseline` 建立 —— 它现在会**顺带**调用只读拓扑探针，
并在响应里多出一个可选的 `surface` 字段。旧页面不看它，因此 L0 响应契约不变。

**② Emission 强度：真机确认后开放写入。** 提交 3A 里它一律只读（`editable: false` +
`readonly_reason: "unconfirmed_capability"`，且不带 binding），因为那时插座名还没在真实
拓扑上确认过。**2026-10-11 真机确认**（Blender 5.2.1 LTS：受管 Cel 组全部命中
`EMISSION` 节点 + `Strength` 插座、`linked=False`，各组值 0.5/0.5/0.42/0.33/0.48/0.44/0.44），
因此开放写入：绑定 `NODE_SOCKET.default_value`，`object_id` = 「组名/节点名/插座名」
（三段**都来自探测结果**，客户端无从提交）。仍降级只读的两种情形：
**插座被上游连线**（写 `default_value` 不生效）、**该组是 reference 角色**。

> 提交 2 里 Emission 强度曾绑定到 `NODE_GROUP.mute`（白名单校验通过、语义完全错误 ——
> 写下去会 mute 整个节点）。现在的绑定是 `NODE_SOCKET.default_value`；「不能写」依旧靠
> 「没有 binding」表达，而不是一句文案。写入时节点/插座缺失 ⇒ 整份计划失败并回滚。

**③ 分组层级 = 子树最高层级。** 提交 2 里 Cel 分组被整组标成 `L3`
（因为子树里有色带），这会让 `max_cost()` 永远返回 `L3`、调度器把「调一个色标」
当成结构性操作。色标的**取值**是 L1；只有色标**数量**属结构信息，而它已由
`element_count` 单独声明为只读 + L3。现在分组取子节点最高层级（Cel 为 L1）。

**④ 色带的 `interpolation` 与 `elements` 同属一个参数。** 客户端提交的复合形态是
`{"elements": [...], "interpolation": "CONSTANT"}`；服务端把它编译成**两条**写入操作
（同一个 datablock 的两个字段），但对外的参数 id 仍是 `cel.<group>.ramp`。
拆分不能让「整体写入、整体回滚」失真，因此两条操作落在同一份计划里、共用一次快照。

**⑤ L0 暂不迁入递归 schema**（原计划在提交 4 批次 1）。原因具体：L0 的 `color.look`
是**依赖枚举**（合法集合由 `color.view_transform` 决定，还要处理 label→identifier 迁移），
而 v4 通用校验器目前只做静态候选比对。现在迁移会让「同一草稿改视图变换 + 改 look」
写出被新视图拒绝的 look。因此提交 3A 里：

* **L0** 继续走既有 `session.validate_draft` + `blender_ops` 写入模板（已被 300+ 用例覆盖）；
* **Cel** 走递归 schema + 通用执行器；
* 两者在 `POST /api/v4/preview` 里编译进**同一个任务**，因此只渲染一次、
  失败时一起回滚，并分别回读校验。`external_changes` / 结构闸门也对两者生效。

迁移工作本身仍属提交 4 批次 1，届时需要同时补齐通用校验器的依赖枚举支持。

**⑥ 失败即恢复 L0 与 Cel 两条基线，并分别报告。** v4 任务的失败响应里
`error.details.restore` 形如：

```json
{"attempted": true, "verified": false, "code": "ROLLBACK_FAILED",
 "l0":  {"attempted": true, "verified": true,  "mismatches": []},
 "cel": {"attempted": true, "verified": false, "mismatches": [...], "error": {...}}}
```

`attempted=false` 表示「尚未写入场景，无需回滚」——**不谎称回滚过**。
没有 Cel 写入时 `cel.verified` 取 `true` 并附 `applicable: false`：整体 `verified`
是两者的与，「无事可做」不该把一次正常的 L0 回滚判成失败。

**⑦ 保存协议接线（结构完整，按钮留到提交 5）。**
`POST /api/session/commit/prepare` / `commit` 新增**可选**的 `surface_draft` 与
`structure_hash`：

* 都不传 ⇒ 行为与旧客户端**逐字节一致**（指纹仍是 L0 草稿指纹）；
* 传了 ⇒ 指纹改为 `{l0, surface}` 的复合指纹，令牌记录 `structure_hash`；
* commit 时：结构指纹不一致 ⇒ `409 STRUCTURE_CHANGED`；
  surface 草稿被改 ⇒ `409 COMMIT_TOKEN_MISMATCH`（且**不落盘**）；
* commit 在写 Cel 之前会**再用只读探针实测一次结构** —— 本地指纹对账证明不了
  「工程这一刻的结构没变」，而结构一变写下去就是错的。

Cel 草稿是**真的会被写进工程**的（否则令牌绑定的就是一份没人执行的草稿，
「用户确认过的内容」与落盘内容将不是一回事）。前端按钮仍不发送它，属提交 5。

```
├── scripts/verify-dist.mjs             npm run build 的最后一步：产物断言

```

> 目录刻意**不叫 `build/`**：`.gitignore` 里的 `build/` 规则会把它（以及 `src/build/`）
> 一起忽略掉，文件会**静默地不进仓库** —— 本地测试全绿、别人拉下来缺文件。
> 这条坑现在由 `tooling/dist-artifacts.test.ts` 的「仓库卫生」用例挡住：
> 它用 `git check-ignore --stdin` 断言 `web/` 下待提交的文件一个都没被忽略。

依赖只有 `preact` 一个运行时包；`vite` / `vitest` / `typescript` / `jsdom` /
`@testing-library/preact` / `@types/node` 都是 devDependencies。**没有引入状态库与组件库** ——
本阶段的状态机（一个 store + 一个命令栈）与虚拟列表都是自研的，加起来不到 400 行，
比引入依赖更可控。

### ② 令牌占位的**位置**才是要点

源 `index.html` 里写了占位注释，但**不能指望它活过 HTML 压缩**。因此插件在
`transformIndexHtml` 的 `post` 阶段**无条件重新插一次**（已存在则原样返回）。
两条产物约束由 `verify-dist.mjs` 与 Vitest 双重断言：`index.html` 恰好一个占位、
`dist/**` 无令牌形态长随机串、无 sourcemap。

> 判据的一个已知取舍：形如 `index-<64 位十六进制>` 的长串会被判为疑似令牌而**误报**。
> 这是刻意的（宁可误报也不漏报），并在用例里固定下来。

### ③ 缓存的两面

| 资源 | 头 | 原因 |
|---|---|---|
| `/next`（HTML） | `no-store, no-cache, must-revalidate` | **它含本次进程的会话令牌**，缓存等于把令牌写进磁盘 |
| `/next/assets/*` | `public, max-age=31536000, immutable` | 文件名带内容哈希 |

静态资源**逐字节直出、不做任何注入** —— 令牌出现在 `.js` 里就会被浏览器缓存。

### ④ 状态机：为什么只有一个 store

`src/state/workspace.ts` 收拢了所有会改状态的路径。三条规则必须在**一处**判定：

* **「结构失效即禁用预览」** —— 散落在组件里必然漏一处；
* **撤销栈与服务端任务历史互不干扰** —— 混在一起会出现「撤销一步把渲染也回滚了」；
* **刷新基线要原子地清掉草稿 + 命令栈 + 任务代次**。

另外 `previewStale` 的语义被刻意收窄为「**有画面**且草稿比画面新」：
还没渲染过时提示是「N 项已改（未预览）」，而不是「画面已过期」—— 两者混成一句会误导。

### ⑤ 命令合并靠 `mergeKey`，不靠时间窗口

`DraftHistory` 用「同类命令 + 相同 `mergeKey` + 栈顶未被 seal」三个条件决定是否合并。
拖动期间每次 `pointermove` 共用同一个 key（`dragElement:<rampId>#<index>`），
`pointerup` 时 `seal()`；键盘输入同理，`blur` 时 seal。
**不同色标的 key 不同，因此永不合并**；复位与复制是原子命令，即使给了 key 也不合并。

快照选的是**完整草稿**而不是逆操作：草稿很小，快照没有「逆操作写错」这类失败模式，
合并也退化成一句「保留第一个 before、替换 after」。

### ⑥ 前端不写浏览器持久存储

草稿引用的 id 与结构指纹都是**会话内**的。加载一份过期草稿比没有草稿更危险 ——
刷新页面即回到基线状态。

### ⑦ L1 的边界：编辑不渲染

Cel 编辑只改草稿；「应用并预览」才提交。提交后**仍可继续编辑**，此时画面对应的草稿已过期，
结果**不会**写进 `effective` 并给出「已标记为过期」的提示。
任务用**递增代次**而不是只靠 AbortController 来丢弃旧结果：abort 只能打断在途请求，
一个已返回、正在被处理的旧响应仍可能走到回调，代次检查才是真正的闸门。

### ⑧ 与「L0 不迁入」的关系

本提交的 schema 只含 Cel。L0 参数（曝光 / 辉光 / 视图变换 / Look）仍是
**只读摘要**（顶部状态栏与图切换用到基线预览），控件留到提交 4。
`/next` 的草稿里可以同时出现 L0 与 Cel 的 id —— 服务端按**基线 schema 的 id 集合**切分，
不认识的一律 `400`。

### ⑨ 结构失效只有**一条**入口（审计修复）

结构失效（`STRUCTURE_CHANGED` / `IDENTITY_MISSING`）必须让草稿作废、命令栈清空、预览禁用。
它有**两个来源**，只处理一个就等于没有保护：

| 来源 | 路径 |
|---|---|
| 同步异常（schema/baseline/预览提交的 HTTP 错误） | `actions.handleError` |
| **预览任务终态**（提交后工程被改、对象被改名） | `JobRunner.onFailed` |

两者统一走 `routeErrorDetail(detail, patch)`：判据只看**稳定错误码**（`isStructureFatalCode`），
不看文案；命中即 `applyStructureFatal`。任务终态另需带上 `activeJob`，因此该函数接受一个
仅用于附加上下文的 `patch`（不得用它覆盖 `error` / `historyBlocked` / `draft`）。

另有一条硬约束：**`clearError` 只清提示，不解除 `historyBlocked`**。
那把锁只能由「成功刷新基线」解除 —— 否则用户点一下横幅上的「关闭」就绕过了
「必须刷新基线」，锁形同虚设。

### ⑩ 拖动状态用 ref 判定，监听器挂在 JSX 上（审计修复）

色带拖动曾有两个真实缺陷：

* `beginDrag` 里 `setDragging(i)` 之后注册的监听器仍闭包捕获 `dragging === null`
  （state 更新要等下一次渲染）→ move 被整段挡掉、up 认不出拖动 → 「拖了没反应」；
* `window.addEventListener` 把**当轮闭包**钉死，`elements` 会发霉。

现在：活动下标放 `useRef`、**判定只读 ref**（state 仅用于渲染高亮）；
`pointermove/up/cancel` 挂在轨道的 JSX 上（每次渲染都是最新 props），
靠 **Pointer Capture** 收全指针移出轨道后的事件；不支持捕获的环境退化为「轨道内拖动」。
轨道宽度为 0（布局未就绪）时不动草稿，而不是写入一个凭 0 宽度算出的位置。

### ⑪ 开发期令牌桥与测试环境保真

* **开发期令牌桥**：页面由 dev server 提供而令牌只在 FastAPI 响应里，`npm run dev` 下写请求
  必然 401。dev server 提供 `apply: "serve"` 的 `GET /__dev/token` 代取一次令牌，
  前端仍只从 `window.__TOON_TUNER_TOKEN__` 读（**生产与开发共用一条读取路径**）。
  插件不进构建产物；不新增暴露面（令牌本来就在 FastAPI 的页面响应里）。
* **jsdom 的 `onpointer*` 缺口**：Preact 按 `"onpointerdown" in element` 选择事件名，
  jsdom 没有这些 IDL 属性时会注册驼峰 `PointerDown`，浏览器语义的 `pointerdown` 打不中。
  `src/testing/setup-dom.ts` 在 `setupFiles` 里补上缺失属性（只补存在性，不伪造行为）。
* **FastAPI 的 422 形状**：默认是 `{detail: [...]}`，不是顶层数组；两种都认，
  否则最常见的校验失败会被显示成 `INTERNAL_ERROR`。

### ⑫ 建立基线要**轮询**首张预览；终态任务离开「活动」位

`POST /api/session/baseline` 会顺带创建「首张基线预览」任务，响应里带着 `job_id` 与
`preview_url`。但**那时图片文件还不存在** —— 直接把 URL 交给 `img`，拿到的要么是 404、
要么是上一张旧图。因此：

* `GET /api/session/baseline` 仍然只读基线；**画面**能不能用由前端轮询该任务决定；
* `JobRunner` 新增 `adopt(jobId)`：跟踪一个**已经提交过**的任务。它与 `start(payload)`
  共用同一套轮询、代次与终态逻辑，只是不负责提交 —— 建立基线的任务由服务端创建；
* 状态拆成两件事：`baselineId`（基线已建立，可调参）与
  `baselinePreviewStatus: none | pending | ready | failed`（那张画面）。
  **只有 `ready` 才把 URL 交给 `img`**；`pending` 显示「正在生成基线预览…」，
  `failed` 明确说「基线已建立，但首张画面未生成」。

**统一终态清理**（`JobRunner.onTerminal`）：成功 / 失败 / 被取代 / 超时 / 提交失败 /
轮询报错 —— 六条路径都必须让任务离开「活动」位，且**恰好触发一次**。
两条相关修正：

* `superseded` 以前什么都不做（只有 `done` / `failed` 有分支），于是被取代的任务会一直
  挂在调用方的 `activeJob` 上 —— 界面显示「渲染中」，实际早已结束；
* 任务结束后**释放 controller**。以前它一直留着，导致「上一个任务已 done」也被判成
  「有活动任务要取代」，`onCancelled` 被无端触发。原先有一条测试把这个错误行为固化了
  （三次顺序提交断言两次取消），本轮按正确语义改正为「顺序提交不触发取消」，
  另加「真正重叠提交才算取代」。

状态字段随之语义收紧：`activeJob` **只放还在跑的任务**，终态快照进 `lastJob`，
状态栏显示「空闲（上次：已完成）」。基线预览被新任务取代时（`AbortController` 只能取消
前端轮询，服务端任务照跑）无法确认文件是否落盘，因此如实改判为 `failed` 并提示重试，
而不是挂一张可能 404 的图。

## 9. 双向覆盖断言（决策 9）

范围**限定为工具声明管理的 binding**：

```python
def test_managed_binding_coverage_is_bidirectional(fake_scene):
    schema = build_schema_from_probe(probe(fake_scene))
    declared = collect_binding_refs(schema)                 # schema 声明
    managed  = managed_object_keys(schema)                  # 受管对象集合
    reported = {b for b in probe_binding_refs(fake_scene) if b.object_key in managed}
    assert declared - reported == set(), "声明了但探测不到"
    assert reported - declared == set(), "探测到但未声明"
```

* 受管范围之外的对象：单独断言被标 `managed: false`，且**不进入**上面的等式；
* 对每个受管 object_type 各跑一次（Cel 组 / 灯光 / 材质 / 相机 / 渲染设置）。

## 10. L0–L3 调度（决策 8）

```
提交草稿 → cost = max(所有变更参数的 cost) → 单次任务（永不拆成多个任务）
```

* L0：300ms 去抖自动提交；
* L1/L2/L3：**不自动**，等用户点「应用并预览」；
* 合并：pending 未开始 ⇒ 与新提交合并，`cost = max(两者)`，只跑一次；
* 取消：沿用「步间检查 superseded」，扩展为每个阶段边界检查一次；
* 排队：单合并工作线程保持串行（Blender 写入不可并发）。
  L0 到达时若高成本任务**尚未开始** ⇒ 合并进 pending 并按最高成本跑；
  **已在执行** ⇒ L0 等待，**不抢占**（抢占会在写入中途打断，风险大于收益）。

性能指标见 §1 决策 8。这些数字**本机无法验证**（无真实 Blender），需真机基准并写入验收记录。

## 11. 预设 v1 → v2 迁移（决策 5）

| 要求 | 实现 |
|---|---|
| 现有 L0 参数无损迁移 | v1 的 10 项 id 与 v2 完全一致（§4.2 是等价迁移），直接取值 |
| 保留名称、创建时间、更新时间 | `created_at` 原样保留；`updated_at` 置为迁移时间并记 `migrated_at` |
| 迁移前为原文件创建备份 | 同目录 `*.v1.json.bak`，沿用预设原子写入的备份范式 |
| 新增参数使用当前基线 | 不伪造默认生效值：v2 新增字段**不落盘**，加载时以基线补齐 |
| 未知字段进兼容性报告 | 进 `report.entries`，**不静默丢弃** |
| 原子写入 + 失败保留 v1 | 迁移写到临时文件后 `os.replace`；失败则保持读取 v1，原文件不动 |

迁移触发点：`GET /api/presets` 读到 v1 时**只报告不迁移**；
`POST /api/presets/migrate` 显式迁移（需令牌）。

## 12. 前端方案（决策 3、4）

### 12.1 目录

```

    ├── main.tsx

    ├── schema/       # toon-surface/2 的 TS 类型 + 分组树 + 过滤/搜索

    └── layout/       # 状态栏 / 导航 / 固定预览 / 检查器 / 底部操作栏
```

* `dist/` **不入库**；`package-lock.json` 入库；
* CI 新增独立 `web` job：`npm ci → tsc --noEmit → vitest run → build`；**pytest 不依赖 Node**；
* 未构建 `dist/` 时服务端返回 **`503 FRONTEND_NOT_BUILT`** 的明确诊断，**不静默返回残缺页面**；
* 发布或人工验收前必须生成对应 commit 的前端产物。

### 12.2 令牌注入的坑

HTML 压缩器可能吃掉注释 ⇒ 占位消失 ⇒ 注入失败 ⇒ **所有写操作 401**。因此：

1. `plugins/token-marker.ts` 在 `transformIndexHtml` 的 `post` 阶段重新插入规范占位；
2. 构建产物断言：`dist/index.html` 必须含 `<!--TOON_TUNER_TOKEN-->`；
3. 反向断言：`dist/**` 与日志中不得出现任何令牌形态的串。

### 12.3 旧页面迁移（决策 4）

## 14. 验收矩阵

### 14.1 自动测试

| 类别 | 覆盖 |
|---|---|
| schema | 所有静态参数有唯一 id / kind / 范围 / binding；白名单字段启动期校验；递归分组 |
| 动态身份 | 身份稳定；重命名 ⇒ `IDENTITY_MISSING`；结构变化 ⇒ `STRUCTURE_CHANGED`；值变化 ⇒ `external_changes` |
| 写入 | 每类 kind 合法写入、越界拒绝、枚举非法拒绝、依赖枚举拒绝、注入拒绝 |
| 调度 | 混合 L0–L3 草稿只执行一次且取最高层级；pending 合并；不抢占 |
| 回滚 | 每个写入阶段故障后的完整回滚 + `rollback` 三态 |
| L3 门禁 | 未通过检查点验收的 L3 参数一律 `editable: false` + `NOT_EDITABLE` |
| 预设 | v1→v2 迁移（备份/原子/失败保留 v1/未知字段进报告）；v2 兼容性报告 |
| 覆盖断言 | 受管 binding 双向差集为空；范围外对象标 `managed: false` |
| 前端 | 搜索/筛选/虚拟化/响应式/命令栈（Vitest，提交 3B + 两轮审计修复后共 159 条） |
| 基线轮询 | queued→running→done 期间不挂图、完成后才给 URL；失败 / 被取代 / 被新任务抢占三种收场 |
| 终态清理 | 成功/失败/被取代/超时/提交失败/轮询报错六条路径各自恰好触发一次；顺序提交不算取代 |
| 结构失效 | 两个来源（同步异常 / **任务终态**）都进入阻断；`clearError` 不解除锁 |
| 色带拖动 | 真实 pointer 生命周期（down→move→up）改草稿、合并且封存历史；只读组不受影响 |
| 开发期 | 令牌桥取到令牌并让写请求带头上；后端不可达时给明确原因 |
| 回归 | 原有 `331 passed, 2 skipped` 不退化（提交 3A 后 464 条；提交 3B 及审计修复后仍 464 条、exit 0） |
