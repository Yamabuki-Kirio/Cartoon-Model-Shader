版本：0.2
日期：2026-10-09
状态：MVP-01 / MVP-02（含预览取景）已实现

> 实现偏差说明：§1 选型表原定本地控制服务用 Node.js，**实际落地为 Python / FastAPI**（见 `src/server/`、`README.md`）。
> 选它的原因是渲染代码生成、白名单校验与测试桩都必须在 Python 侧表达，与 Blender 端同语言可省掉一层翻译。

## 1. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | 原生 HTML / CSS / JavaScript，浏览器打开 | 需求已明确；色带、取色器、滑块、A/B、缩放组件成熟；与 Blender 进程解耦 |
| 本地控制服务 | **Node.js**（22.x） | 与前端同语言；WebSocket 生态成熟；单进程管理任务队列与文件 IO 足够 |
| 前后端通道 | HTTP（初始化/预设/文件）+ WebSocket（状态/预览推送） | 需求 §4.2、§12 |
| Blender 通信 | 直连现有 MCP `127.0.0.1:9876` | 需求决策 3：复用现有端口，**不另装通信插件** |
| 保存/备份 | Node `fs` + 时间戳副本 | 需求 §14 |

> 不使用固定 `sleep`；一律以 `job_id` + 状态查询等待。

## 2. 已探明的 Blender MCP 协议（实测）

插件本体：`%APPDATA%\Blender Foundation\Blender\5.2\scripts\addons\blender_mcp.py`
进程实测：`127.0.0.1:9876` LISTENING。

**传输层**：TCP socket。客户端发送**一个完整的 JSON 对象**（如 `{"type": "ping", "params": {}}`）；服务端把命令排入队列，由 Blender 主线程的 timer 取出执行，再把响应 `json.dumps` 后 `sendall` 回客户端。

**注意（与需求文档的差异）**：响应**没有换行分隔符**，不是严格的行分隔 JSON。收发两侧都是「累积缓冲 → 尝试 `json.loads` → 成功即视为一条完整消息」。因此客户端必须做增量 JSON 解析，不能按 `\n` 切分。

**响应格式**：`{"status": "success" | "error", "result": {...}}`。

**可用命令（只读相关）**：

- `ping` → `{"status":"success","result":{"pong":true}}`（无 bpy 访问，用于纯粹连通性探测）
- `get_scene_info` —— 场景、相机、渲染引擎等
- `get_world_state_snapshot`
- `get_addon_info`
- `get_object_info`
- `list_scene_items`
- `get_viewport_screenshot`
- **`execute_code`** —— 在 Blender 主线程执行任意 Python，返回结果 ★ 桥接层的关键入口

**桥接层结论**：MCP 原生没有协议版本、任务 ID、能力查询、错误码、状态查询等高级语义。这些将由本地控制服务在 MCP 之上**自建会话协议层**实现：

1. 所有写操作/渲染都通过 `execute_code` 下发，并在 Python 侧包一层返回 `{job_id, ok, effective_values, warnings, elapsed, image_path}`。
2. 由于 MCP 不主动推送，控制服务对长任务采用**短间隔非阻塞轮询**（`job_id` 查询脚本注入的进度变量），不使用固定 sleep。
3. 若后续发现 `execute_code` 无法满足（例如需要跨命令保持 Python 进程内状态），则在 Blender 端以一个**常驻 Python 模块**（经 `execute_code` 首次加载后驻留 `bpy` 模块命名空间）承载会话状态。

## 3. 三层架构

```
浏览器 Web UI  ⇄(HTTP+WS)⇄  本地控制服务(Node)  ⇄(TCP JSON)⇄  Blender MCP :9876  ⇄  Blender 主线程
```

- **本地控制服务**：校验参数 schema/类型/范围与模式适用性；任务排队、取消、去抖；保存预设/缩略图/运行记录；向前端推送状态。默认仅监听 localhost，启动时生成随机令牌校验请求。
- **Blender 桥接**：读当前场景与角色、建/查卡通管线、采集真实参数、从基线恢复、应用参数集、执行预览/正式渲染、回传实际生效参数与警告。

## 5. MVP 最小闭环（首个里程碑）

```
连接 9876 → 读取当前场景 → 建立基线 → 调整曝光/辉光(L0)
  → 自动预览（去抖 250–400ms）→ 恢复基线 → 保存预设
```

拆分任务：

1. **M1 连通性**：控制服务连上 9876，`ping` + `get_scene_info` 并在前端状态栏显示。
2. **M2 会话协议层**：`execute_code` 封装、`job_id` 分配、状态查询、错误码。
3. **M3 基线**：读取受控属性/节点插座/灯光/修改器 → 内存快照；初始化成功即出基线预览。
4. **M4 L0 参数**：曝光、Gamma、辉光五参数等；前端草稿 → 去抖 → 完整草稿应用 → 预览。
5. **M5 无污染校验**：连续预览后受控灯光/节点/修改器数量不增加；恢复基线后关键状态与快照一致。
6. **M6 预设**：保存/加载 JSON 预设（含 configured / effective / active 三套值）。

验收见需求文档 §17。

## 6. 预览取景（构图）实现设计

对应需求文档 §20。模块：`src/server/framing.py`。

### 6.1 构图唯一真源：`camera.data.view_frame()`

不自己推导 lens / sensor_fit / shift_x / shift_y / 渲染纵横比的组合效果，一律以 Blender 的
`camera.data.view_frame(scene=scene, apply_shift=True)` 返回的四个角点为唯一真源。

**关键陷阱（实测踩过）**：`view_frame()` 返回的三个向量**不在单位距离上** —— 与 `sensor_fit` 平行的方向上，半高恒为 `0.5`，
深度方向实测 `z ≈ -2.854`，并不是 `z = -1`。若直接拿 `x/y` 当「单位距离处的半宽/半高」用，`shift` 会被放大数倍，
算出「无论多远都装不进画面」的错误结果（首版得到 `distance = 16777216`、`worst = 1.4666`）。

正确做法：先用 `depth = -max(zs)` 把四个点归一化到单位距离，再取 `half_w / half_h / cx / cy`（`cx/cy` 即 shift 在画面上的等效偏移）。

修正后实测（`Duo_Vertical_MMD_Camera`，lens 68.4966 / VERTICAL / shift (0.4, -0.16)）：
`half_w = 0.0956`、`half_h = 0.1752`、`cx = 0.1402`、`cy = -0.0561`。这也解释了为什么 shift 必须站在 fit 方向的传感器尺寸口径上理解。

### 6.2 入画判定

世界点 `P` 在相机空间 `q = R^T (P - C)`；`u = q.x / q.z + cx`、`v = q.y / q.z + cy`（注意 Blender 相机朝 `-Z`，故用 `-q.z` 作深度）。
完整入画当且仅当 `|u| <= half_w` 且 `|v| <= half_h`。

越界比例按需求口径报「超出画面边长的比例」：`overflow = max(0, -min_u - 1)` 之类，而不是简单取 `min`，这样「自动取景后全 0」才成立。

### 6.3 自动取景解析解

不迭代试探，直接解：对包围盒每个角点 `(a, b, c) = R^T @ (corner - aim)`，要求 `|a| / (d - c) <= hw` 且 `|b| / (d - c) <= hh`，
取 `d = max_corner( c + max(|a| / hw, |b| / hh) )` 即最小可行距离。安全边距通过把 `hw / hh` 除以 `(1 + margin)` 实现：
15% 边距即 `hw / 1.15`，实测 `worst_ndc = 0.869565 = 1 / 1.15`，与理论值精确吻合。

临时相机朝向沿用原相机的旋转（因此仍保持工程的美术视角），shift 归零，只解算距离。

### 6.4 角色筛选

按骨架分组，取面数最多的一组为主要角色。排除规则：`rigid_body` 代理、命名模式匹配（`outline` / `shell` / `描边` / `轮廓` / `rigid` / `物理` / `刚体` / `インジケータ` / `ガイド` / `ダミー` / `操作`）、
`hide_render`、不可见、无材质槽。本工程实测：139 个网格里 138 个是带「物理」材质的刚体代理，唯一角色是 `model_mesh`（35544 面）。

### 6.5 临时相机生命周期

`bpy.data.cameras.new` + `bpy.data.objects.new` + `scene.collection.objects.link` 创建；
渲染体包在 `try/finally` 里，`finally` 中先恢复 `scene.camera = 原相机`，再 `bpy.data.objects.remove` / `bpy.data.cameras.remove`。
三个清理动作各自独立 `try/except`，保证任一环节抛错都不会阻断后续恢复 —— 渲染失败也一定能还原。

### 6.6 基线失效闸门

`framing.build_context_code()` 是**只读探针**，返回 frame / camera / transform / lens / shift / 角色包围盒 / 投影结果。
`session.submit()` 在建任务**之前**调用 `_assert_framing_fresh()`：先跑一次只读探针，与基线快照比对，
硬失效（帧变、相机变、位移、旋转、焦距、shift）直接抛 `FRAMING_STALE`（409，retryable），软告警只附在结果里。

渲染脚本另带 `_expect_frame` / `_expect_camera` 双重校验，即使闸门与渲染之间发生竞态，渲染体内也会主动中止，不会产出误导性画面。

### 6.7 白名单与无注入

取景代码与参数代码一样是**白名单驱动生成**：`framing.validate_options()` 只接受 `mode`（4 个 Literal 之一）与 `margin`（`0 <= m <= 0.4`），
未知字段一律 `PARAM_INVALID`；`REGION_RULES` 等字面量经 `repr` 量化后注入，客户端无法夹带任意 Python。

### 6.8 预览分辨率

按工程分辨率等比缩放到**长边 990**，保持纵横比（`binder.preview_resolution_for`）。取景诊断与实际渲染必须共用同一画面形状，
否则「入画」判定与实际画面不一致。本工程 1080×1980 → 540×990，与旧固定值巧合一致。
