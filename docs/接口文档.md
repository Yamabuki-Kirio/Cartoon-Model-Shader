# 接口文档

> 适用版本：`0.1.0` · 最后更新：2026-10-09
> 服务默认监听 `http://127.0.0.1:8765`（**仅回环**，配置成远程地址会被直接拒绝）。

本文是接口的唯一权威。README 只保留速查表，细节以本文为准。

---

## 1. 通用约定

### 1.1 会话令牌（所有写接口）

* 进程启动时用 `secrets.token_urlsafe(32)` 生成**一个随机令牌**。
* 令牌只通过 `GET /` 的**页面响应**注入前端：

  ```html
  <script>window.__TOON_TUNER_TOKEN__ = "<令牌>";</script>
  ```

  静态文件 `src/web/index.html` 里只有一个占位注释 `<!--TOON_TUNER_TOKEN-->`，
  **磁盘上不存在任何带令牌的文件**；日志、错误响应、`/openapi.json` 里都不会出现它。
* 校验方式：请求头 `X-Toon-Tuner-Token: <令牌>`，服务端用 `hmac.compare_digest` 做常量时间比较。
* **全部 POST 接口（＝本服务的全部写接口）都强制校验**；缺失或错误一律：

  ```json
  {"ok": false, "error": {"code": "SESSION_TOKEN_INVALID", "message": "写接口需要有效的本机会话令牌。",
   "retryable": false, "hint": "...", "details": {"header": "X-Toon-Tuner-Token", "reason": "missing"}}}
  ```

  HTTP `401`。`reason` 只有 `missing` / `mismatch` 两种取值，**绝不回显令牌内容**。
* 只读接口（所有 `GET`）不需要令牌。

> 为什么只监听回环还不够：浏览器里的**任意网页**都可能向 `http://127.0.0.1:8765`
> 发起不需要预检的跨站请求。写接口一旦没有令牌闸门，一次误触发就可能写坏 `.blend`。

### 1.2 错误信封

所有失败响应形状固定：

```json
{
  "ok": false,
  "error": {
    "code": "稳定错误码",
    "message": "面向用户的中文说明",
    "retryable": true,
    "hint": "下一步该做什么",
    "details": { "...": "可选诊断，默认脱敏本机路径" }
  }
}
```

`INVALID_DEPENDENT_ENUM` 的 `details` 会额外**平铺**到 `error` 顶层，便于前端直接读
`parameter` / `value` / `depends_on` / `allowed`。

### 1.3 路径与代码注入

* **不接受任何 Python / 命令文本**：请求里塞 `code` / `python` / `command` 等字段，
  新接口一律 `422`（Pydantic `extra="forbid"`）；Blender 侧只执行服务端内置的固定模板。
* 所有进入模板的字面量都经 `repr()` 量化，路径里的引号、反斜杠只是**普通字符**。
* 「预设」接口**没有任何路径字段**：目录来自服务端配置，文件名由服务端从名称派生
  （`<ascii 摘要>-<sha256 前 16 位>.json`），因此路径穿越在结构上不可能发生。
* 例外（有意为之）：`应用到工程` 的**确认信息**会展示目标绝对路径与预计备份路径 ——
  这是「覆盖前必须让用户看清写到哪」的硬要求，仅出现在该确认载荷中，不进日志。

## 2. 只读接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 单页界面（注入会话令牌） |
| GET | `/api/health` | 服务存活检查 |
| GET | `/api/blender/status` | 快速探测端口与协议，**始终 200**，用 `status` 区分 |
| GET | `/api/blender/scene` | 完整只读场景探针 |
| GET | `/api/params/schema` | L0 参数白名单（驱动前端动态生成控件） |
| GET | `/api/session/baseline` | 当前内存基线；未建立时 `409 NO_BASELINE` |
| GET | `/api/framing/context` | 当前帧 / 相机 / 相机动画 / 角色是否入画 + 基线是否失效 |
| GET | `/api/color/looks` | 某视图下 Blender **真正接受**的 Look 档位 |
| GET | `/api/jobs/{job_id}` | 任务状态；未知 id → `404 JOB_NOT_FOUND` |
| GET | `/api/preview/{job_id}` | 取回预览 PNG（浏览器唯一的取图入口）；任务未完成 → `404` |
| GET | `/api/presets` | 列出本地预设 |

`status` 取值：`connected` / `disconnected` / `timeout` / `protocol_error` / `blender_error`。
任务 `status` 取值：`queued` / `running` / `done` / `failed` / `superseded`。

     "created_at": "…", "updated_at": "…",
     "pipeline_mode": "faithful", "framing_mode": "auto_full_body", "framing_margin": 0.15,
     "preview_quality": "standard", "parameter_count": 10, "active_count": 10}

## 3. 预览相关写接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/blender/reconnect` | 重置连接状态并立即重新检测 |
| POST | `/api/session/baseline` | 采集内存基线（含取景快照）+ **立即**产出首张预览任务 |
| POST | `/api/session/restore` | 回滚到基线并逐项校验 |

`POST /api/preview` 请求体：

```json
{"draft": {"color.exposure": 1.0, "color.look": "AgX - High Contrast"},
 "framing": {"mode": "current_camera", "margin": 0.15}}
```

依赖枚举非法 → `400 INVALID_DEPENDENT_ENUM`（且**不产生任务、不碰 Blender**）。

## 4. 预设：本地保存与加载

预设 = **运行设置 + 完整草稿**的快照，存在本机用户目录，**不进仓库**。
除 `GET` 外的所有写接口都需要会话令牌（见 §1.1）。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/presets` | 列表 + 运行设置白名单（见 §2.1） |
| GET | `/api/presets/{preset_id}` | 读取单个预设（含逐参数三元组） |
| POST | `/api/presets` | 新建预设（`201`） |
| PUT | `/api/presets/{preset_id}` | 覆盖保存；`preset_id` 与 `created_at` 由服务端保留 |
| POST | `/api/presets/{preset_id}/rename` | 重命名（**身份不变**） |
| POST | `/api/presets/{preset_id}/duplicate` | 复制为新预设（**新身份**，`201`） |
| DELETE | `/api/presets/{preset_id}` | 删除预设 |

### 4.1 请求体（`POST` / `PUT`）

```json
{
  "name": "夜战·高对比",
  "schema": "toon-tuner-preset/1",
  "pipeline_mode": "faithful",
  "framing_mode": "auto_full_body",
  "framing_margin": 0.15,
  "preview_quality": "standard",
  "parameters": {
    "color.exposure": {"configured_value": 0.5, "effective_value": 0.5, "active": true},
    "glow.threshold": 1.6
  }
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | ✔ | 显示名与去重键，**支持中文**；`1–80` 字符 |
| `schema` | ✖ | 省略即按当前版本写入；旧版本会得到明确的 `PRESET_SCHEMA_UNSUPPORTED`，而不是被字段校验挡成笼统的 422 |
| `pipeline_mode` / `framing_mode` / `framing_margin` / `preview_quality` | ✖ | 运行设置。**`pipeline_mode` 当前仅存储，尚未接入 Blender 执行**，界面也不应呈现为「已生效」 |
| `parameters` | ✖ | 参数 id → 取值。值可以是 `{configured_value, effective_value, active}` 三元组，也可以是**裸取值**（视作 `configured = effective = 该值` 且 `active = true`） |

**没有任何路径字段**：目录与文件名全部由服务端决定，路径穿越在结构上不可能发生。
未知顶层字段一律 `422` 拒绝（`extra="forbid"`）。**不需要建立基线**即可保存。

成功响应（`POST` / `PUT` / `rename` / `duplicate` 同构）：

```json
{"ok": true, "preset": {"preset_id": "1a2b3c4d5e6f7a8b", "name": "夜战·高对比",
 "schema": "toon-tuner-preset/1", "created_at": "…", "updated_at": "…",
 "pipeline_mode": "faithful", "framing_mode": "auto_full_body", "framing_margin": 0.15,
 "preview_quality": "standard", "parameter_count": 2, "active_count": 2,
 "parameters": {"color.exposure": {"configured_value": 0.5, "effective_value": 0.5, "active": true}}}}
```

`DELETE` 返回 `{"ok": true, "deleted": {…PresetSummary…}}`。

### 4.2 身份与文件名

`preset_id` 与磁盘文件名**解耦**：重命名不改变身份（前端已有引用不会失效），
复制生成**新身份**。名称只参与「显示」与「去重」，绝不参与路径拼接。

### 4.3 存储与原子写入

落盘位置：`%LOCALAPPDATA%\CartoonModelShader\presets`；
可用环境变量 `TOON_TUNER_PRESET_DIR` 覆盖（优先级高于默认位置），
或用配置项 `presets.dir` 显式指定。
写入方式：`mkstemp` → `flush` + `fsync` → `os.replace`，失败路径清掉临时文件，
**不会留下半截 JSON**；目录扫描显式排除点开头的临时文件。

### 4.4 失败

| 情况 | 状态码 | 错误码 |
|---|---|---|
| 缺令牌 / 令牌错误 | 401 | `SESSION_TOKEN_INVALID` |
| 预设不存在 | 404 | `PRESET_NOT_FOUND` |
| 名称或取值非法、含禁止保存的本机路径/凭据 | 400 | `PRESET_INVALID` |
| `schema` 版本不受支持 | 400 | `PRESET_SCHEMA_UNSUPPORTED` |
| 同名冲突（**不区分大小写**） | 409 | `PRESET_NAME_CONFLICT` |
| 目录读写失败（磁盘 / 权限 / `os.replace` 失败） | 500 | `PRESET_STORAGE_ERROR` |
| 请求含多余字段（如 `path`） | 422 | FastAPI 校验错误 |

> 预设**禁止保存**本机敏感内容：`.blend` 绝对路径、用户目录、模型/贴图路径、
> MCP Token、临时预览路径。命中即**拒绝**（拒绝而非静默清洗），
> 且接口只回可展示位置，不回本机绝对路径。

## 5. 应用到工程

两段式：`prepare` 只校验并把「写到哪、备份放哪」摊开给用户看；`commit` 才真正落盘。
两段之间用**一次性短效令牌**绑定，杜绝「看过 A 却存成 B」。

### 5.1 `POST /api/session/commit/prepare`

**需要令牌。**

```json
{"mode": "save_as", "draft": {"color.exposure": 0.5}, "target_path": "<盘符>:\\<工程目录>\\模型_导出.blend", "confirm": false}
```

| 字段 | 说明 |
|---|---|
| `mode` | `save_as`（默认）/ `overwrite` |
| `draft` | 完整草稿；校验同预览 |
| `target_path` | **仅 `save_as` 使用**：绝对路径、须以 `.blend` 结尾、父目录必须存在 |
| `confirm` | 覆盖已有文件时必须为 `true` |

目标路径的确定规则：

* `save_as`：来自 `target_path`；若该文件**已存在**，按「覆盖」对待 —— 同样要求二次确认并生成备份，
  **绝不允许静默覆盖**用户文件。
* `overwrite`：目标**只能**是 Blender 当前工程（`bpy.data.filepath`）；请求里带 `target_path` →
  `400 SAVE_TARGET_INVALID`。工程没保存过 → `409 PROJECT_NOT_SAVED`。

**覆盖需要二次确认**：`confirm` 不为 `true` 时**不签发令牌**，返回 `409 SAVE_CONFIRM_REQUIRED`，
其 `details` 就是让用户核对的那份信息：

```json
{"code": "SAVE_CONFIRM_REQUIRED", "message": "即将覆盖已有文件：<绝对路径>。需要看清绝对路径与备份位置后二次确认。",
 "details": {"mode": "overwrite", "target_path": "<目标绝对路径>", "backup_path": "<预计备份绝对路径>",
             "warnings": ["将覆盖当前已保存的工程文件。保存前会在同目录生成带时间戳的可恢复备份。",
                          "Blender 里存在未保存的改动：本次备份只能备份磁盘上「上一次保存的版本」，……"],
             "confirm_required": true}}
```

> ⚠ **未保存改动的警告**：当 `bpy.data.is_dirty` 为真时，磁盘上的 `.blend` 是**上一次保存的版本**，
> 因此**本次备份只包含那一版，不包含当前未保存的改动**；而这些改动会在本次保存中一并写入工程文件
> （其中受本工具管理的曝光/辉光参数会被设成当前草稿值）。界面必须把这个警告显示出来。

成功响应：

```json
{"ok": true, "token": "<一次性令牌>", "mode": "overwrite",
 "target_path": "<目标绝对路径>", "backup_path": "<预计备份绝对路径>", "warnings": ["…"],
 "baseline_id": "…", "draft_hash": "…", "parameter_count": 10, "normalized": [],
 "expires_at": "2026-10-09T16:22:00+08:00", "expires_in_seconds": 120, "confirmation_required": true}
```

令牌有效期 **120 秒**，一次性；服务端同时最多保留 32 张待确认票据。

### 5.2 `POST /api/session/commit`

**需要令牌。** 消费令牌并执行保存。

```json
{"token": "<prepare 返回的令牌>", "mode": "overwrite", "draft": {"color.exposure": 0.5}, "target_path": null}
```

`draft` / `mode` / `target_path` 必须与 prepare 阶段**完全一致**（覆盖模式下 `target_path` 可省略或原样回传）。

执行顺序（不可跳步）：

> **第 0 步：复核确认时的前提。** commit 开始时会先确认「确认那会儿」的备份前提是否仍然成立：
> 确认时目标存在、现在却消失了 → `BACKUP_FAILED`（无法按已确认路径备份）；
> 确认时目标不存在、现在却出现了 → `SAVE_CONFIRM_REQUIRED`（覆盖它需要重新确认，会先生成备份）。
> 这两种情况都在**写场景之前**拦下，因此 `status.applied` 仍为 `false`、也不会触发回滚。

1. **应用完整草稿** —— 与预览同一套规范化规则（基线 + 草稿，含 Look 依赖迁移）；
2. **回读校验** —— 逐项比对实际写入值，**不一致就不保存**；
3. **备份**（仅覆盖时）—— 在目标同目录生成 `<主干>.bak-<时间戳>.blend`（保留 `.blend` 扩展名，
   改名回去即可在 Blender 里直接打开）；**备份失败就拒绝覆盖**；
   **路径用的是 prepare 阶段算出的那一条**（见下），commit 不重新计算；若该路径已被占用，
   直接拒绝（不销毁已有备份），要求重新准备以取到新时间戳；
4. **保存** —— `save_as` 用 `bpy.ops.wm.save_as_mainfile(check_existing=False)`（关掉 UI 覆盖确认框），
   `overwrite` 用 `bpy.ops.wm.save_mainfile()`；保存后回读 `bpy.data.filepath` 与 `is_dirty` 校验；
5. **刷新基线** —— 工程内容已变（就是这份草稿），重新采集基线，避免后续预览「恢复到旧基线」。

成功响应：

```json
{"ok": true, "mode": "overwrite", "target_path": "<绝对路径>", "backup_path": "<备份绝对路径>",
 "saved": true,
 "status": {"applied": true, "readback_verified": true, "mismatches": [],
            "backup": {"required": true, "created": true, "path": "<备份绝对路径>", "path_confirmed": "<同一路径>"},
            "rollback": {"attempted": false, "verified": false, "mismatches": [], "code": null, "error": null,
                         "reason": "保存成功，未触发回滚。"},
            "saved": true, "target_path": "<绝对路径>", "mode": "overwrite", "draft_preserved": true,
            "applied_values": {"color.exposure": 0.5, "…": "…"},
            "save": {"path_after": "<绝对路径>", "path_matches": true, "file_exists": true, "is_dirty_after": false}},
 "steps": ["复核确认时的前提", "应用完整草稿", "回读校验", "生成备份", "保存工程", "刷新基线"],
 "normalized": [], "baseline_id": "<新基线>", "baseline_refreshed": true,
 "saved_at": "…", "warnings": ["…"]}
```

失败时**一定不会保存**，并且会**尝试把 Blender 恢复到提交前的基线**：
草稿已经写进场景，不恢复的话界面显示的参数与 Blender 里的实际取值就会脱节。

失败响应的 `error.details` 里带 `status`（五态）与 `steps`：

```json
{"code": "APPLY_VERIFY_FAILED",
 "message": "草稿写入后回读不一致，已中止保存（磁盘上的工程文件未被写入）。 已恢复到提交前的基线，并回读校验通过。",
 "details": {"status": {
    "applied": true, "readback_verified": false, "mismatches": [{"id": "color.exposure", "expected": 0.4, "actual": 0.9}],
    "backup": {"required": false, "created": false, "path": null, "path_confirmed": null},
    "saved": false, "draft_preserved": true,
    "rollback": {"attempted": true, "verified": true, "mismatches": [], "code": null, "error": null, "reason": null}},
  "steps": ["复核确认时的前提", "应用完整草稿", "回读校验"]}}
```

`status.rollback` 的语义：

| 字段 | 说明 |
|---|---|
| `attempted` | 是否尝试过回滚。前提复核阶段就拦下的失败为 `false`（尚未写场景，无需回滚） |
| `verified` | 回滚后**回读校验**是否通过。只有它为 `true` 才可以说「已恢复到提交前的基线」 |
| `mismatches` | 回滚回读仍不一致的项 |
| `code` | 回滚没能确认成功时为 `ROLLBACK_FAILED`，否则 `null` |
| `error` | 回滚失败时内层的错误信封（含原因） |

> **顶层错误码始终是原始失败原因**（`APPLY_VERIFY_FAILED` / `BACKUP_FAILED` / `SAVE_FAILED`），
> 回滚结果只作为附加信息 —— 否则「为什么失败」就被盖掉了。
> 回滚失败时错误文案会直说「Blender 里的取值可能仍不是提交前的状态，请人工确认」，
> 并在 `rollback.code` 里点名 `ROLLBACK_FAILED`。

前端据此显示「应用 / 回读 / 备份 / 保存 / 失败后回滚」各自做到哪一步；草稿始终保留在界面上。

### 5.3 令牌与失败错误码

| 情况 | 状态码 | 错误码 |
|---|---|---|
| 缺令牌 / 令牌错误 | 401 | `SESSION_TOKEN_INVALID` |
| 未建基线 | 409 | `NO_BASELINE` |
| 目标非法（相对路径 / 非 `.blend` / 目录 / 父目录不存在） | 400 | `SAVE_TARGET_INVALID` |
| 覆盖模式却带 `target_path` | 400 | `SAVE_TARGET_INVALID` |
| 覆盖未确认 | 409 | `SAVE_CONFIRM_REQUIRED` |
| 覆盖但工程从未保存 | 409 | `PROJECT_NOT_SAVED` |
| 令牌不存在 / 格式不对 | 409 | `COMMIT_TOKEN_INVALID` |
| 令牌已过期 | 409 | `COMMIT_TOKEN_EXPIRED` |
| 令牌已用过（一次性） | 409 | `COMMIT_TOKEN_USED` |
| 模式 / 目标 / 草稿与 prepare 不一致 | 409 | `COMMIT_TOKEN_MISMATCH` |
| 基线已变化（被刷新或重新采集） | 409 | `BASELINE_STALE` |
| 回读不一致（**未保存**，并回滚基线） | 502 | `APPLY_VERIFY_FAILED` |
| 备份失败（**未覆盖**，并回滚基线） | 500 | `BACKUP_FAILED` |
| Blender 保存失败（**未保存**，并回滚基线） | 502 | `SAVE_FAILED` |
| 确认之后目标才出现（需重新确认） | 409 | `SAVE_CONFIRM_REQUIRED` |
| 请求含多余字段 | 422 | FastAPI 校验错误 |

另有一个**不作为顶层错误码**的稳定标记：`ROLLBACK_FAILED` —— 它只出现在
`error.details.status.rollback.code`，表示「尝试过回滚但未能确认恢复」，见上文。

## 6. v4 过渡接口（Cel 竖切，提交 3A）

迁移期间新页面用这四个接口，**旧页面继续用 `§2–§5` 的接口，行为一行不改**。
除 `POST` 外都是只读接口，因此按既有规则不校验会话令牌。

### 6.1 `GET /api/v4/surface/schema`

递归 schema。每个节点都带四件状态（`supported` / `editable` / `active` /
`readonly_reason`）与三值（`value` / `baseline` / `effective`）。

色带是**单一复合节点**（`kind: "ramp"`，内含 `elements` 与 `interpolation`），
刻意不展开成 2N 个独立 id —— ColorRamp 是单个 datablock，整体写入才原子；
UI 仍为每个色标渲染独立的 position / color 控件。

```json
{"ok": true, "schema_version": "toon-surface/2", "highest_cost": "L1",
 "surface_baseline_id": "…", "structure_hash": "…", "degraded": ["Cel_Hair", "…"],
 "groups": [{"id": "cel.Cel_Skin", "kind": "group", "supported": true, "editable": true,
   "children": [
     {"id": "cel.Cel_Skin.ramp", "kind": "ramp", "cost": "L1", "editable": true,
      "binding": {"object_type": "COLOR_RAMP", "object_id": "Cel_Skin/ColorRamp", "field": "elements"},
      "elements": [{"index": 0, "position": {"value": 0.0, "baseline": 0.0, "minimum": 0.0, "maximum": 1.0},
                    "color": {"value": [0.05, 0.05, 0.08, 1.0], "baseline": [0.05, 0.05, 0.08, 1.0]}}],
      "interpolation": {"value": "LINEAR", "baseline": "LINEAR", "options": [{"value": "CONSTANT", "label": "常量"}]},
      "element_count": {"value": 3, "baseline": 3, "structural": true, "cost": "L3",
                        "editable": false, "readonly_reason": "rollback_unavailable"}},
     {"id": "cel.Cel_Skin.emission_strength", "kind": "float",
      "supported": true, "editable": false, "readonly_reason": "unconfirmed_capability",
      "value": 1.5, "baseline": 1.5, "effective": 1.5},
     {"id": "cel.Cel_Skin.managed_mode", "kind": "enum", "editable": false,
      "readonly_reason": "structural", "value": "editable"}]}]}
```

* `supported: false` ⇒ 当前工程里探不到（**不猜 socket 名**），`reason` 给出原因；
* `editable: false` ⇒ 只读，`readonly_reason` 取值见 `surface/schema.py`：
  `not_found` / `rollback_unavailable` / `reference_only` / `structural` /
  `unconfirmed_capability`（`unconfirmed_capability` = 探到了但真机插座名尚未确认，
  因此拒绝写入 —— Emission 强度即属此类）；
* 只读节点**不带 `binding`**：拒绝写入靠的是「结构上不可写」，不是一句文案。

无基线时 `409 NO_BASELINE`。

### 6.2 `GET /api/v4/session/baseline`

v4 基线。建立基线请调用 `POST /api/session/baseline`（它会顺带采集这里的 v4 状态）。

```json
{"ok": true, "available": true, "baseline_id": "…", "structure_hash": "…",
 "compositor_group": "AI_Compositor", "found_groups": 7, "declared_groups": 8,
 "degraded": ["Sakura_Hair_Reference"],
 "identities": [{"object_type": "NODE_GROUP", "name": "Cel_Skin", "source": "AI_Compositor"}],
 "values": {"cel.Cel_Skin.ramp": [{"position": 0.0, "color": [0.05, 0.05, 0.08, 1.0]}]}}
```

只读拓扑探针**失败**时（例如 Blender 忙）：`available: false` + `error`，
本接口回 `502`（原始错误码）。刻意**不**退化成「探不到所以全都 supported:false」——
那会把一次真实的 Blender 故障伪装成「你的工程里没有 Cel 组」。L0 基线不受影响。

### 6.3 `POST /api/v4/preview`（需令牌）

```json
{"draft": {"cel.Cel_Skin.ramp": {"elements": [{"position": 0.38, "color": [0.58, 0.46, 0.43, 1.0]}],
                                  "interpolation": "CONSTANT"},
           "color.exposure": 0.5},
 "framing": {"mode": "current_camera", "margin": 0.15},
 "expected_structure_hash": "…"}
```

草稿里可以同时出现 **L0 参数 id**（走既有校验路径）与 **Cel 参数 id**
（走递归 schema + 通用执行器）。判定依据是**基线 schema 里的 id 集合**，不是字符串前缀；
两边都不认识的 id 一律 `400 PARAM_INVALID`（不静默丢弃）。

任务序列是固定的：

```
检查身份与结构 → 恢复基线（L0 + Cel）→ 应用完整草稿 → 回读校验 → 渲染预览 → 恢复基线并校验
```

* 身份缺失 ⇒ `IDENTITY_MISSING`；结构变化 ⇒ `STRUCTURE_CHANGED` —— 两者都在
  **任何写入之前**判定，且 `restore.attempted = false`（没写过就不声称回滚过）；
* 值层外部改动（例如用户在 Blender 里拖了一下色标）**只报告**，进 `result.external_changes`，
  不作废草稿 —— 否则工具会变得完全不可用；
* 提交阶段就拒绝的：草稿越界（`PARAM_INVALID`）、色标数量变化（`STRUCTURE_CHANGED`）、
  `expected_structure_hash` 与基线不符（`STRUCTURE_CHANGED`）。这三类**不产生任务**；
* 失败时 `error.details.restore` 分开报 L0 与 Cel 两部分的恢复结果（见下文）。

成功结果的关键字段：

```json
{"preview_url": "…", "applied": {"color.exposure": 0.5},
 "applied_surface": {"cel.Cel_Skin.ramp": [...], "cel.Cel_Skin.ramp.interpolation": "CONSTANT"},
 "restored": {"color.exposure": 0.0},
 "restored_surface": {"cel.Cel_Skin.ramp": [...]},
 "restore_verified": true, "surface_restore_verified": true,
 "structure_hash": "…", "external_changes": [], "steps": [...], "framing": {...}}
```

**失败任务不会替换最后一张成功预览**：图片端点只服务 `done` 任务，
失败任务的 `job_id` 取不到图，前端自然保留上一张成功的。

### 6.4 `GET /api/v4/jobs/{job_id}`

与 `GET /api/jobs/{job_id}` 共用同一份任务存储（排队与「新任务取代旧任务」同一套机制）。
v4 任务多一个 `"kind": "surface"` 字段，并在有外部改动时带 `external_changes`。

### 6.5 失败与恢复状态

v4 任务失败时，`error.details` 形如：

```json
{"steps": ["检查身份与结构", "恢复基线", "应用完整草稿", "回读校验"],
 "restore": {"attempted": true, "verified": false, "code": "ROLLBACK_FAILED",
             "l0":  {"attempted": true, "verified": true,  "mismatches": []},
             "cel": {"attempted": true, "verified": false, "mismatches": [...], "error": {...}}},
 "external_changes": []}
```

* 顶层 `error.code` 始终是**原始失败原因**（`SURFACE_APPLY_FAILED` / `APPLY_VERIFY_FAILED` /
  `PREVIEW_FAILED` / `IDENTITY_MISSING` / `STRUCTURE_CHANGED` …），
  `ROLLBACK_FAILED` 只出现在 `restore.code`，不覆盖前者；
* `attempted: false` ⇒ 尚未写入场景，无需回滚（**不谎称回滚过**）；
* 没有 Cel 写入时 `cel.applicable = false`、`cel.verified = true`。

### 6.6 保存协议（可选参数）

`POST /api/session/commit/prepare` 与 `POST /api/session/commit` 新增**两个可选字段**：

| 字段 | 说明 |
|---|---|
| `surface_draft` | v4 参数面草稿。传了就一并绑进确认令牌；被改动 ⇒ `COMMIT_TOKEN_MISMATCH` |
| `structure_hash` | 客户端持有的结构指纹。与基线不符 ⇒ `409 STRUCTURE_CHANGED` |

**都不传 ⇒ 行为与旧客户端完全一致**（令牌指纹仍是 L0 草稿指纹，响应里
`structure_hash: null`、`surface_parameter_count: 0`）。

传了之后：

1. `prepare` 用「`{l0, surface}` 复合指纹」签发令牌，并记下 `structure_hash`；
2. `commit` 复核结构指纹 → **再用只读探针实测一次结构**（本地指纹对账证明不了
   工程这一刻没变）→ 应用 L0 草稿 → 应用 Cel 草稿 → 逐项回读 → 备份 → 保存；
3. 任一步失败都不落盘，并恢复 L0 与 Cel 两条基线。

> 提交 3A 里前端「保存」按钮**不发送**这两个字段（留到提交 5）；
> 接口侧已经完整可用且被测试覆盖。
